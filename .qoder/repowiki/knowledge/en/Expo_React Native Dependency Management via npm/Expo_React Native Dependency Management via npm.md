## System / Approach

This is an Expo-based React Native application that manages third-party dependencies exclusively through npm (Node Package Manager). There are no Go modules, vendored packages, private registries, or lockfile overrides beyond the standard package-lock.json generated by npm.

The project uses the Expo CLI (expo start, expo run) as its build and development toolchain, which in turn resolves native module linking for iOS/Android platforms.

## Key Files

- package.json — The single source of truth for all runtime dependencies, scripts, and metadata. Declares 18 direct dependencies including Expo SDK, React Navigation, Supabase JS client, React Native Maps, and various Expo platform modules (auth-session, image-picker, location, status-bar, web-browser).
- package-lock.json — The npm lockfile that pins exact transitive dependency versions, ensuring reproducible installs across environments.
- eas.json — Expo Application Services configuration; while not a dependency manifest itself, it influences how native builds resolve platform-specific dependencies during cloud builds.

## Architecture and Conventions

### Versioning Strategy

Dependencies use a mix of version specifiers:
- Exact versions (no prefix): react@19.1.0, react-native@0.81.5, react-native-maps@1.2.0.1, @react-native-async-storage/async-storage@2.2.0. These are pinned to a specific patch release.
- Caret ranges (^): @react-navigation/native@^7.3.0, @supabase/supabase-js@^2.107.0, expo@^54.0.35. Allows minor/patch updates within the major version.
- Tilde ranges (~): expo-auth-session@~7.0.11, expo-dev-client@~6.0.21, expo-image-picker@~17.0.11, expo-location@~19.0.8, expo-status-bar@~3.0.9, expo-web-browser@~15.0.11, react-native-safe-area-context@~5.6.0, react-native-screens@~4.16.0. Locks to the latest patch within the specified minor version.

This mixed strategy appears driven by Expo's ecosystem compatibility matrix rather than a uniform policy — Expo-managed packages tend to be pinned tightly (tilde) to match the declared expo SDK version, while other libraries use caret ranges for flexibility.

### No Vendoring

There is no vendor/, node_modules/ committed to the repository, and no custom registry configuration (no .npmrc, no registry field in package.json). Dependencies are resolved from the public npm registry at install time.

### Private Registry / Auth

No private npm registry, authentication tokens, or scoped package configurations were found. All dependencies come from the public npm registry.

### Scripts

The scripts section defines four commands (start, android, ios, web) that delegate entirely to the expo CLI. There are no custom dependency update, audit, or upgrade scripts (e.g., no update-deps, audit-fix, etc.).

## Conventions and Constraints

- Single manifest: All dependencies are declared in one flat dependencies block under package.json; there are no devDependencies, peerDependencies, or workspace-level separation.
- Lockfile enforced: package-lock.json is present and should be kept in sync with package.json to ensure deterministic installs.
- Expo SDK alignment: The expo package version (^54.0.35) acts as the anchor for compatible versions of the expo-* family packages; mismatches would likely cause Expo prebuild/build failures.
- Private package flag: The "private": true field prevents accidental publishing to the npm registry, treating this repo as an internal application rather than a library.
- No peer dependency declarations: The codebase does not declare peerDependencies, so consumers (if any) are not guided on required host versions of React/React Native.

## Update Workflow Implications

Given the absence of automated tooling (no Dependabot, Renovate, or CI jobs visible), dependency updates appear to be performed manually via npm install <pkg>@<version> followed by committing both package.json and package-lock.json. The tilde-pinned Expo modules suggest updates should be coordinated around Expo SDK releases to maintain compatibility.
